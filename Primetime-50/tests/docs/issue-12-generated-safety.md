## Production contract

`POST /api/ai/plan` checks origin, authenticates with `requireUser`, bounds JSON to 1 KiB and accepts exactly `{request_id: UUID}`. It rejects caller profiles, health, eligibility, approval, identity, model and policy assertions. There is no automatic actionable demo fallback. A key alone cannot enable a call: the server requires explicit `PRIMEFIT_GENERATED_PROVIDER_ENABLED=approved-live-v1`, a server-only OpenAI key, storage configuration, and a separately approved database provider activation and exact eligible policy/catalogue. No activation data is seeded. This text documents future gates; it does not authorise setting them.

The server calls `reserve_generated_workout` with the authenticated owner through a service-only RPC. Ordinary authenticated/anonymous callers cannot reserve, finalise, forge provenance or mutate approvals. The existing reviewed resolver validates the saved profile/health/equipment, rejects unknown health, referral/clearance restrictions and unstructured health notes, and requires exact approved context equality. Every allowed catalogue entry must still be approved and compatible. Policies and catalogue records are immutable versioned content; revocation is permitted, rewriting or deleting history is refused. Professional approval remains Austin5's responsibility.

The minimal provider context contains only policy ID, context revision, saved frequency/duration limits, week rules and allowed catalogue IDs/session durations. It contains no name, email, DOB, weight, raw health notes, cross-user data, keys or user ID. Nothing accepts caller prose. The provider can select only schedule slots and reviewed catalogue IDs. The policy's week-by-week catalogue matrix explicitly permits progression combinations; it does not let the model invent load, reps, substitutions, nutrition, extra instructions or guidance. The exact reviewed prescription and its progression/stop/referral instructions are attached by storage. This minimum pipeline generates a schedule of approved prescriptions; it does not freely invent new exercise prescriptions.

Strict validation rejects missing/unknown keys, bad IDs/types, wrong policy/context revision, missing/extra weeks, frequency violations, duplicate/out-of-order days, incompatible durations and insufficient rest including across week boundaries. Both the server validator and SQL persistence enforce the contract. Eligibility and current approval are rechecked at save, not just in the prompt or at reservation. SQL stores a distinct owned generated plan with confirmed selection, exact policy rules, context revision, model/activation/reservation provenance and reviewed prescription/version/reviewer/source snapshots. No raw health snapshot is saved in generated tables. POST returns only confirmed storage data, with no-store. Replaying the request ID returns the stored plan only after current admission recheck. Historical RLS reads retain historical approval provenance and are not current admission.

## Atomic limits and failures

The reservation transaction uses the existing context/catalogue serialisation lock plus a written budget MVCC fence. Concurrent attempts, different request IDs, retries and multiple application processes share global UTC daily reserved-cost and per-user daily/cooldown decisions. The written fence forces stale repeatable-read transactions to fail rather than bypass an aggregate budget check. All calls reserve their full approved per-call ceiling permanently; failures are not refunded. Repeated failed/expired IDs never initiate a second provider call. Reservations expire for saving after 30 seconds. A crashed pending attempt remains spent and non-retryable. The service never automatically retries reservation RPCs.

The fixed provider endpoint is `https://api.openai.com/v1`, fixed model `gpt-4o-mini`, zero SDK retries, 8 KiB context ceiling, 2,048 output-token ceiling, 16 KiB accepted response ceiling and 10-second abort/deadline. Approval records must independently review current pricing for this complete input/output envelope and the per-call reserve, user/global caps and cooldown. The schema's conservative minimum reservation is USD 0.10; it is an accounting reservation, not an observed provider charge or a claim of current pricing. Global daily approved reserved cost is capped in schema at USD 10; no spend is authorised by this source. Keys or environment settings alone cannot create a policy/activation approval record.

Provider outage, timeout, truncation, refusal, malformed/adversarial/incompatible output, budget exhaustion, absent/revoked policy/catalogue, changed saved context or save failure produce no newly usable plan and no provisional prescription response. Raw provider exceptions are suppressed. A save transport failure can leave an unknown commit outcome: the response says to reload, and exact-ID replay can confirm a committed plan without another provider call. A failed cancellation cannot revive an expired reservation.
