## Implemented contract

`/app/nutrition` server-verifies identity and redirects to login on refusal; `/nutrition` shares the production logger under existing middleware. The existing home import also receives the updated component. There is no new AI/provider dependency. Meal description and entered protein, including zero, and water are user records, not endorsed prescriptions. Austin decision **#10 remains OPEN**; no calorie/protein/water target, deficit, meal recommendation, remaining amount or progress ring is introduced. Exercise approval #5 remains with Austin.

The baseline `meal_logs` stores meals/macronutrients without mutation receipts, revision or timezone; there is no baseline water-entry table. An additive unified `nutrition_entries` contract avoids silently reinterpreting or changing legacy retained records. Legacy `meal_logs`, `nutrition_targets`, food suggestions and habit data are neither copied into nor counted as new logs. The log explicitly shows only its owned saved entries. The shared AppShell now truthfully describes entered meals/protein/water without personalised targets and says saving requires configured account services. Coach/library sample qualifiers, history, unavailable analytics and reviewed-workout caveats are preserved. This is not connected persistence or target approval. No source9 delivered input was changed.

Entries store an explicit calendar `logged_on` date and IANA `timezone`. Viewing selects that exact pair; changing a device timezone never changes stored entries. Initial date uses the current instant in the displayed device zone, including DST. The selected calendar day runs midnight to next midnight in that zone; entries are assigned dates, not inferred from creation timestamps. Editing date or timezone moves the entry; both destination saved content and the current viewed day are read back. There is no latest-N truncation of a day's totals. SQL aggregates the complete owned day and its entries in one statement snapshot. The client rejects duplicate IDs, mismatched dates/zones, malformed entries or inconsistent totals.

Protein is stored as **integer tenths of a gram**, displayed in g. Water is **integer mL**. Raw decimal syntax is validated without coercion or rounding: protein allows one decimal place and zero; water requires a positive whole number. Technical representability limits are 0–100000 protein tenths, 1–100000 mL per entry, dates 1900–2100, 300 description characters and bounded revisions. These are storage limits, not recommended consumption, targets or clinical decisions. Missing protein is refused rather than invented as zero.

`GET /api/nutrition?day=YYYY-MM-DD&timezone=IANA` and `POST /api/nutrition` use the existing verified-auth service and origin/body-size/JSON error architecture. Every successful/error response has `Cache-Control: no-store`. Caller ownership/authority fields are rejected. `POST` explicitly carries `action=create|update|delete` and an opaque UUID `mutation_id`; entries use UUID identity and expected revision (delete carries `id,expected_revision`). Updates cannot change entry kind. SQL independently checks types, unknown keys, ownership, dates, timezone, values and revisions; malformed/refused operations roll back.

The migration grants authenticated SELECT under owner-only RLS, with no admin/metadata exception; direct writes and receipt reads are denied. Narrow `SECURITY DEFINER` RPCs with empty search paths are required for atomic entry/receipt mutation without granting clients direct writer access. They explicitly predicate every data lookup/update/delete on `auth.uid()`, reject missing identity, revoke PUBLIC/anon execution and grant only the intended authenticated RPCs. Internal validator execution is revoked. New table policies do not change any pre-existing policy. This follows the [Supabase grants and RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security); actual configured platform execution is unproven.

Mutation receipts are durable database records keyed by `(user_id,mutation_id)`. Same identity plus identical JSON returns the original acknowledgement without repeating effects; changed payload under that identity conflicts. Per-owner transaction locks serialize mutations; revisions prevent stale edits/deletes. A replay of an old create after edit/delete never undoes the edit or resurrects the deleted record. The mutation and receipt commit together. Receipts intentionally remain until the owning auth user is deleted; no pruning process is added.

The client retains one exact payload and mutation identity for an ambiguous network/acknowledgement/readback outcome. It locks further edits and offers Retry same change and saved-day reload; it never reports success from a mutation response alone. It validates acknowledgement ID/action/revision and rereads exact saved values. Definitive 404/409/422 refusals retain input, allow correction and instruct comparison with reloaded saved rows. A confirmed acknowledgement with subsequently changed saved values keeps local input and offers an explicit use-current-saved/discard action. No localStorage/sessionStorage or persisted browser health data is used. Pending identity is memory-only in the mounted controller; refresh/unmount does not automatically resend. The UI explicitly tells users leaving an unconfirmed change to inspect saved entries before entering it again. Durable deduplication lives in SQL receipts; no cross-refresh automatic retry claim is made.

Loading, true empty, delayed, error, retry and signed-out states are separate. Totals are absent when saved facts cannot be confirmed. Errors retain raw draft inputs. Deletion has a confirmation/cancel step. Labels, units, live status/alerts, native date inputs, button semantics, focus on the editor and wrapping responsive layout use the existing visual system. No new framework/dependency is introduced. Auth is reverified before and after responses; auth callback changes clear records, pending payload and draft. Epoch checks stop stale read/write/identity/error responses from publishing into another activation or after unmount. Already dispatched writes cannot be undone by unmount; their receipt remains at the authenticated database boundary.
