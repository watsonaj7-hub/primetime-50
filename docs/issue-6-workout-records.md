## API and service

All endpoints require a verified user. Mutations require same-origin JSON, authenticate before reading the body, then validate strict fields. Services independently authenticate direct callers. Mutation successes and read successes are `Cache-Control: no-store`. No client-supplied owner, parent reference, prescription, review claim, completion time or unit is accepted.

- `POST /api/workouts`: `{id, mode: "personal", timezone}`. Client generates one UUID per intended recording and retains it across retries. An identical start returns the existing owned recording without resetting it; a different timezone for the ID conflicts. `mode: "reviewed"` is a reserved unavailable boundary, not a content approval path.
- `PUT /api/workouts`: `{id, expected_revision, sets: [...]}`. Each set has `{id, exercise_key, exercise_name, set_number, reps, weight, rpe}`. UUID `id` identifies that exact set for its lifetime. UUID `exercise_key` groups user-entered sets; it is not a reference to a prescribed exercise or another user's record. Name/key/slot cannot change for an existing set. A unique `(log, exercise_key, set_number)` prevents duplicate slots.
- `POST /api/workouts/complete`: `{id, expected_revision}`. Complete only after all intended saves are confirmed and the caller has acknowledged their returned revision. Completion returns the original completed record on subsequent valid retries, even if their revision is old.
- `GET /api/workouts?id=<uuid>` reopens one owned personal recording with saved sets; no matching/foreign record yields an empty array. Without `id`, returns at most 100 recent personal recordings, including drafts, sorted by start instant descending then UUID descending. This bounded read is not a complete paginated history UI. Sets sort by exercise UUID, set number, then set UUID. Legacy rows are preserved and not silently recast as new records.

Mutation response: `{workout: <saved log row>}` including revision and completion state. Read response: `{workouts: [<log with exercise_set_logs>]}`. Errors are controlled 401/403/400/413/415/422, 404 for inaccessible managed records, 409 for conflicts/incomplete completion/unavailable reviewed content, or 503 for unconfirmed storage outcomes. Database details are not returned.

## Draft/save/complete and retries

Start creates revision 0, `completed=false`, no sets and no completion timestamp. Reps are whole numbers 0–100; load is finite kg 0–10000; RPE is numeric 1–10; set number is whole 1–20; labels are trimmed 1–200 characters. Each save contains 1–100 distinct sets. These are recording bounds, not recommended training values. Explicit null reps/load/RPE are allowed drafts. Missing fields are rejected; null is an intentional clearing edit. UI callers must retain unsaved input when any save fails.

Each save is one SQL transaction: authorise/lock the owned log, compare revision, update/insert the supplied stable set IDs, increment revision. No omission deletes a set; no delete/rename endpoint is provided. An invalid second set rolls back the first change and the revision too. Previously committed batches survive. Concurrent/stale saves return conflict instead of overwriting newer values. If a response is lost, retrying the same revision either succeeds once or returns 409; reload the same ID and reconcile saved values before resubmitting unsaved input. A 503 does not assert either persistence or completion. There is no client-controlled success flag.

Completion locks the same log as saves, checks the acknowledged revision, and requires at least one saved set with non-null reps/load/RPE in every set. It changes the existing log once, not inserts history rows. Failed/incomplete/stale completion does not modify sets, revision or completion time. Concurrent completion and replay return the one stored result/timestamp. Saved completed records reject later service writes. Completion cannot detect an intended edit that never reached the server; #7 must not call it after an unconfirmed/failed save.

## Provenance, time and preservation

The server fixes and freezes `prescription_snapshot` to `{source:"user_recorded",version:1,prescription:null,weight_unit:"kg"}`. This is an honest provenance envelope, **not** a reviewed prescription snapshot. Existing plans/days/exercises cannot be used to assert review. Enabling reviewed starts later requires a separately reviewed migration/resolver that copies a trusted versioned prescription and source/approval identity atomically, enforces screening, and preserves historical snapshots when catalogue content changes. Never accept that snapshot from the client.

`performed_at` is the server start instant; `completed_at` is the database clock instant of the first successful completion (`timestamptz`, returned as an offset/UTC instant). There is no backdating endpoint. The caller must choose a recognised timezone at start; SQL validates it against PostgreSQL timezone names. Freeze that timezone for the recording. Group completed history by the completion instant converted to the stored timezone, never by the current device timezone; use start instant for drafts. DST is resolved by the database timezone rules. #8 owns the eventual history UI. Weight stays kg regardless of profile display-unit preference.

The additive migration marks old rows with NULL `record_mode`; it does not infer missing historical timestamps, snapshots or approvals. Existing same-owner composite FKs, legacy writes and owner-only reads remain. Managed logs and their sets cannot be inserted/edited/deleted directly by authenticated users: existing RLS write policies are narrowed only for managed records, with owner reads retained. Bounded security-definer RPCs have empty search paths, derive `auth.uid()`, validate payloads at SQL seams and grant execution only to authenticated users. Helpers are not callable by clients. There is no admin read exception or new provider dependency.
